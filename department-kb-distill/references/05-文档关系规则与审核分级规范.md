# 文档关系规则与审核分级规范

## 1. 原则

关系建设分为“本地召回候选”和“Codex双端核验”两步。候选不等于关系成立，文本相似或同目录不能直接成为正式关系。

## 2. 稳定ID与关系记录

底层一条关系一行，至少记录：关系ID、来源/目标稳定ID、标题、链接、创建者、类型、方向、通俗含义、双方证据、风险、审核级别、状态、两端内容哈希、权限和时间。

页面`relations`只保存已通过关系，例如：

```yaml
relations:
  - relation_type: "前置依赖"
    relation_meaning: "执行本流程前需确认该制度。"
    related_object: "<稳定ID>"
```

## 3. R01—R10候选规则

| 规则 | 判断方法 | 证据强度 | 用途 |
|---|---|---|---|
| R01 完全重复 | 两端规范化SHA-256一致 | 强 | 可自动确认重复事实 |
| R02 直接链接 | A正文包含B钉钉链接 | 强 | 明确引用候选 |
| R03 稳定ID | A正文出现B稳定ID | 强 | 明确引用候选 |
| R04 标题引用 | 引用动词后标题唯一匹配B | 中 | 制度/文档依据候选 |
| R05 版本表达 | 标题主体相同并有新版、替代、废止等词 | 中 | 版本候选；效力需L3 |
| R06 相同业务编号 | 项目号、工单号、制度号一致 | 中 | 同业务对象候选 |
| R07 输入输出匹配 | A产出与B输入明确匹配 | 中 | 上下游候选 |
| R08 类型互补 | 同一对象下制度—流程—模板—案例互补 | 中 | 实施关系候选 |
| R09 文本相似 | BM25/TF-IDF排名靠前 | 弱 | 只排序，不能单独成立 |
| R10 路径上下文 | 同项目或专题目录 | 弱 | 辅助证据，不能单独成立 |

候选门槛：至少一条强证据，或两条相互独立的中证据。每份文档保留候选上限应在任务配置中明确。

## 4. 建议正则骨架

```text
稳定ID:       \b[A-Z][A-Z0-9_-]{1,20}-[A-F0-9]{12}\b
钉钉链接:     https://alidocs\.dingtalk\.com/(?:i/)?(?:nodes|spaces)/[A-Za-z0-9_-]+
标题引用:     (?:依据|参照|按照|详见|见|引用|遵循)\s*[《“\"]([^》”\"]{2,100})[》”\"]
版本词:       新版|旧版|最新版|修订|替代|取代|废止|失效|沿用|v\d+(?:\.\d+)*
项目号:       \bPRJ[-_ ]?\d{3,}[A-Z]?\b
制度号:       \b[A-Z]{2,10}[-_/]\d{3,}(?:[-_/]\d+)?\b
工单号:       \b(?:TICKET|WORK|BUG|REQ)[-_]?\d{3,}\b
```

部门特有编号必须在任务配置中补充。正则只负责召回，不能代替语义核验。

## 5. Codex双端核验

Codex必须同时阅读双方全文或可验证证据，输出：

- 成立、驳回或需人工确认；
- 关系类型和方向；
- 面向业务人员的一句话解释；
- 来源和目标各自的原文证据位置；
- 风险标记和审核级别；
- 是否覆盖双方全文。

不得把模型归纳句标成原文引句。清单中引用证据时，应给出原句所在完整段落或准确位置。

## 6. L0—L3分级

| 级别 | 含义 | 处理 |
|---|---|---|
| L0 | 哈希等确定事实可直接证明 | 自动通过 |
| L1 | 正文直接点名或链接，Codex核对一致 | 自动通过并抽样 |
| L2 | 普通业务关系，双方证据完整且无高风险 | 自动通过，事后抽样 |
| L3 | 冲突、废止/替代效力、权限泄露或制度效力 | 发布前逐条人工确认 |

Codex返回`needs_review`时，即使初始标为L2，也必须升级到L3。

## 7. 面向负责人的L3清单

每条只展示：

```text
两份文档标题
两份原文创建者
两份原文链接
存在什么关系
这段关系是什么意思
负责人需要确认什么
```

规则编号、关系ID、置信度、系统标签和技术证据放后台台账，不堆在业务主清单中。

## 8. 一对多与权限

一份文档可关联多份文档，底层逐边保存，页面按关系类型聚合。展示前取两端运行时ACL交集；无权限用户不得看到受限目标的标题、链接、摘要、稳定ID、关系含义或存在性提示。
