# 角色分工与部门协作规范

知识库蒸馏不是单纯的文件转换。技术执行负责完整性和可追溯性，业务负责人负责业务口径，权限负责人负责可见范围，知识库负责人负责最终交付。

## 一、角色职责

| 角色 | 主要职责 | 必须确认的内容 |
|---|---|---|
| 部门知识库负责人 | 发起任务、确定范围、组织审核、批准交付 | 处理范围、分类体系、发布版本 |
| 业务负责人 | 判断业务含义、有效口径和高风险关系 | L3关系、冲突、废止和制度效力 |
| 权限负责人 | 判断文档和关系的访问边界 | 敏感范围、跨权限关联、发布权限 |
| 本次任务发起人 | 使用AI执行本规范，并作为本次执行审核人 | 处理范围、执行结果和技术验收；在AI对话框明确确认后触发成功文档由候选转为正式 |
| Codex | 盘点、下载、解析、提取、建页、关系核验和质检 | 技术完整性、证据可追溯、失败清单 |
| DWS 操作者 | 读取钉钉源数据，获批后发布并回读 | 空间、节点、权限和回读结果 |
| 普通使用者 | 通过目录、搜索或 Codex 使用知识库 | 反馈错误、过期和缺失内容 |

## 二、责任边界

### Codex 可以直接完成

- 基于正文生成摘要、关键词、场景和内容特征。
- 执行确定性规则，生成关系候选。
- 阅读双方正文并判断普通语义关系。
- 自动通过 L2 关系，并生成抽样清单。
- 生成本地双目录页面、关系台账和失败清单。

### 业务负责人必须参与

- 确认互相矛盾的业务口径哪一个有效。
- 确认旧制度是否废止、被替代或仍然并行有效。
- 确认制度、通知、会议纪要等不同文档的效力顺序。
- 确认敏感关系是否可以展示，以及展示给哪些人。
- 确认无法从原文判断的状态、版本或高风险业务口径；Owner不需要确认，固定取创建者。

### 不应要求业务负责人逐条确认

- 文件哈希、稳定ID、目录路径、创建者和Owner等确定性字段。
- 有明确正文证据且无冲突、无权限风险的 L2 关系。
- 普通主题相似但未作为正式关系发布的低优先级候选。

## 三、推荐协作流程

1. 任务发起人提交启动信息和处理边界，并自动成为本次执行审核人。
2. 执行人完成只读盘点，提交源文件清单和异常项。
3. 执行人完成本地蒸馏，提交审核入口、失败清单和 L3 清单。
4. 业务负责人仅处理 L3 和缺失事实，不逐份审核所有文档。
5. 本次任务发起人作为执行审核人，检查L2抽样关系和页面质量；确认整批无误时在AI对话框明确表达“确认此次蒸馏没有问题”或同等含义，系统记录原话并把哈希未变化的成功文档由“候选”改为“正式”。
6. 权限负责人确认敏感目录和跨权限关系。
7. 知识库负责人签署发布清单。
8. 若任务启动配置已提供最终写回目录并启用 `publishing`，由 DWS 操作者发布并回读；未配置时只交付本地结果。

## 四、抽样规则

- L2 默认自动通过，建议初次任务抽查 20%。
- 若抽样错误率不超过 5%，可按既定比例继续。
- 若抽样错误率高于 5%，应暂停发布、修正规则并扩大抽样。
- 涉及制度、合规、财务、人事和权限的 L2，可提高抽样比例。
- 抽样记录应包含抽样范围、错误类型、修正动作和复验结论。

## 五、交接物

每轮蒸馏至少交付：

- 任务配置和源库快照信息；
- 源文件盘点清单；
- 原目录镜像和业务知识目录；
- 17 字段元数据和完整原文入口；
- 关系总览、L2 抽样清单和 L3 确认清单；
- 解析失败清单；
- 本地验收结果；
- 如已发布，补充发布清单和回读报告。

## 六、变更与升级

- 业务规则变化：由知识库负责人批准，并记录规则版本。
- 分类体系变化：保留旧分类到新分类的映射，避免稳定 ID 变化。
- 关系口径变化：重新计算候选并复核受影响关系。
- 源文档更新：使用来源更新时间和内容哈希判断是否需要重蒸馏。
- 发布范围变化：重新执行权限检查和发布门禁。
