# 双目录页面与统一AI检索元数据规范

## 1. 双目录定义

```text
部门知识库
├── 01-Raw原目录镜像
│   └── 按来源相对目录逐层组织
└── 02-业务知识目录
    ├── 00-知识库管理
    ├── 01-导航与知识地图
    ├── 10—89-部门业务分类
    ├── 90-跨域专题
    └── 99-历史归档
```

两套目录中的对应页面均为完整蒸馏知识页。业务分类由各部门根据真实工作场景制定，不复制其他部门目录。

## 2. 页面标准结构

```markdown
# 文档标题

## AI检索元数据（17字段与蒸馏画像）

一个固定结构的YAML区块

## Raw Mirror

[打开来源或对应原目录页面]

## 相关知识

- 关联文档名称
- 两份文档存在什么关系
- 这段关系是什么意思
- 可点击的关联文档链接

## Original Content

完整原文
```

非文本材料将最后一段改为`Original Attachment`并提供原附件链接。本地审核页可以额外显示“待业务确认的相关知识”；正式页面不得发布未确认的重要关系。

完整原文保留业务内容和可见链接，但必须移除附件临时下载地址中的`Signature`、`AccessKeyId`、`Expires`和安全Token等短期参数。能定位父文档时改为父文档链接，否则只保留不含查询参数的资源地址。

## 3. 页首统一区块

### 3.1 为什么只保留一个区块

17字段负责文档管理和状态判断；蒸馏画像负责理解文档主题、对象和业务动作。两者都属于AI初筛信息，因此合并到同一个页首YAML区块。不得再单独生成“AI检索卡”“标准元数据（17字段）”或“蒸馏画像”，避免同一信息重复、版本不一致和额外Token消耗。

### 3.2 固定结构

- 区块必须紧跟文档标题，使DWS只读页首0—1号block即可取得；
- 顶层固定为`schema_version`、`stable_id`、`view`、`metadata`、`distillation_profile`；
- `metadata`内固定保存17字段；
- `distillation_profile`内固定保存7项语义画像；
- 两套视图除`view`外必须完全一致；
- Schema以`schemas/ai-document-header-v2.json`为准。

```yaml
schema_version: "kb-ai-document-v2"
stable_id: "<稳定ID>"
view: "原目录视图"
metadata:
  title: "<来源文档标题>"
  page_type: "流程"
  scenario: ["<业务场景>"]
  keywords: ["<关键词一>", "<关键词二>"]
  summary: "<仅依据原文生成的事实摘要>"
  owner: "<钉钉原文创建者姓名或待补充>"
  status: "候选"
  processing: "已蒸馏"
  version: "1.1"
  source: "<SOURCE_URL>"
  source_updated_at: "<YYYY-MM-DD HH:mm:ss>"
  content_hash: "sha256:<64位十六进制>"
  sources: ["<SOURCE_URL>"]
  blindspots: []
  relations: []
  property_generated_at: "<YYYY-MM-DD HH:mm:ss>"
  property_updated_at: "<YYYY-MM-DD HH:mm:ss>"
distillation_profile:
  core_theme: "<核心主题>"
  business_objects: ["<业务对象>"]
  document_role: "<文档在业务中的作用>"
  inputs: ["<输入>"]
  actions: ["<动作>"]
  outputs: ["<产出>"]
  constraints: ["<约束>"]
```

## 4. 固定17字段

字段不得增减、改名或在画像中重复保存：

```text
title, page_type, scenario, keywords, summary, owner, status,
processing, version, source, source_updated_at, content_hash,
sources, blindspots, relations, property_generated_at, property_updated_at
```

| 字段 | 含义 | 规则 |
|---|---|---|
| `title` | 当前标题 | 与来源当前标题一致 |
| `page_type` | 页面类型 | 制度、流程、指标、常见问题、案例、概念、总览 |
| `scenario` | 使用场景 | 说明谁在何时使用 |
| `keywords` | 检索词 | 核心词，不堆砌同义词 |
| `summary` | 摘要 | 只概括原文明确事实 |
| `owner` | 内容负责人 | 固定取钉钉原文创建者姓名；仍不可得才写待补充 |
| `status` | 业务状态 | 候选、正式、已失效、待确认 |
| `processing` | 加工状态 | 已蒸馏或平台字符限制-原附件保全 |
| `version` | 属性规范版本 | 不是原文制度版本 |
| `source` | 主来源 | 来源页面或文件链接 |
| `source_updated_at` | 来源更新时间 | 使用来源元数据 |
| `content_hash` | 内容指纹 | 完整正文或原附件SHA-256 |
| `sources` | 补充来源 | 来源链接数组 |
| `blindspots` | 有证据的缺口 | 不填写模型猜测风险 |
| `relations` | 已通过关系 | 未通过门槛不得写入 |
| `property_generated_at` | 首次生成时间 | 本属性首次生成时间 |
| `property_updated_at` | 最近更新时间 | 最近一次重算或修改时间 |

字符串数组没有内容时必须写`[]`。`relations`是对象数组，没有已通过关系时写`[]`。

`正式`只能由本次任务执行审核人在AI对话框明确确认整批蒸馏无误后产生。确认记录必须保存确认人、原话、时间和每份文档内容哈希；来源哈希变化后，对应文档自动回到`候选`。

### 4.1 `relations`对象

```yaml
relations:
  - relation_type: "<通俗关系名称>"
    relation_meaning: "<两份文档如何配合使用的通俗解释>"
    related_object: "<关联文档稳定ID>"
```

技术规则编号、置信度和审核过程只保存在关系台账，不进入页面字段。“完全重复”只证明内容一致，不代表可以删除，也不决定版本优先级。

### 4.2 不进入17字段的数据

来源相对路径、父节点、下载尝试、解析器、失败原因、Raw/业务页面地址、权限快照、发布状态、回读状态、Codex调用次数和双页面校验结果属于执行台账，不得增加为页面字段。

## 5. 页面一致性

同一稳定ID在两套目录中必须满足：

- 页首统一区块除`view`外一致；
- Original Content或Original Attachment一致；
- 已发布关系、状态、Owner和内容哈希一致；
- 任一页面更新时，另一页面同步更新。

## 6. 事实优先级与目录索引

完整原文或原附件是事实源；页首统一AI检索元数据用于检索、导航和初步理解；关系台账是审核事实源；本地执行台账是加工与审计事实源。

原目录视图和业务分类视图的每一层文件夹都生成`目录索引.md`。目录索引只列当层子目录、当层文档、类型/状态、场景和一句话说明；根目录另生成`00-AI问答与检索入口`和`00-AI知识库地图`，不生成罗列全库文档的巨大索引。
