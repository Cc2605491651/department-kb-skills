# 部门知识库增量维护

本Skill负责“发现变化和编排增量”，`department-kb-distill`仍是唯一蒸馏、渲染、发布与回读引擎。两者必须配套安装。

## 必须读取

开始时读取：

1. `references/incremental-workflow.md`
2. `references/health-rules.md`
3. 全量基线任务的`00-config/task-config.yaml`

需要定时运行或发布时再读取`references/scheduling-and-safety.md`。

## 固定门禁

- 来源知识库始终只读。
- 首次维护时从已验收全量任务创建一个独立增量目录；后续轮次持续复用该增量目录，不在全量目录中直接加工。
- `--stage all`只生成本地结果，不发布、不更新成功基线。
- 本地结果、扫描快照、增量计划和工作清单通过哈希绑定；旧验收不能用于新一轮。
- 只有执行审核人在AI对话框明确确认后，才能提交本地基线或发布。
- 发布必须单独执行`--stage publish`；发布失败或回读失败时不得更新成功基线。
- 不自动删除、归档、判定失效、移动线上节点或修改线上权限。

## LLM 提供方选择

维护过程中涉及大模型的阶段（新增文档的语义画像、关系核验）与 `department-kb-distill` 共用同一选择：执行前询问用户用 codex 订阅额度还是第三方大模型。第三方时按 distill 的规则注入环境变量，并用 distill 的 `run_pipeline.py` 传参执行（`--llm-provider` / `--llm-model` / `--llm-api-key-env` / `--no-ai-cache`），API key 只经环境变量传入，不写文件、不进台账。

## 标准执行

### 1. 首次创建独立增量任务

```bash
python3 <MAINTAIN_SKILL_ROOT>/scripts/create_incremental_job.py \
  --baseline-job <已验收的全量任务目录> \
  --job <新的独立增量任务目录>
```

该命令只在首次执行。它复制已验收清单、缓存、关系台账、双目录页面和原发布目标，不复制临时发布授权，也不改全量目录。以后每轮都复用这个增量目录，以保留变化快照和审核历史。

### 2. 生成本地结果

```bash
python3 <MAINTAIN_SKILL_ROOT>/scripts/run_maintenance.py \
  --job <增量任务目录> --stage all --workers 4
```

若用户只要求扫描预览，增加`--dry-run`。执行结束后，在AI对话框直接汇报`00-增量结果与下一步.md`的结论，并让用户抽检`01-本次增量审核入口.md`。

### 3. 明确确认

只有用户在AI对话框明确表达“确认本次增量蒸馏没有问题/审核通过”后执行：

```bash
python3 <MAINTAIN_SKILL_ROOT>/scripts/run_maintenance.py \
  --job <增量任务目录> --stage confirm \
  --confirmation-text "<用户确认原话>" \
  --confirmed-by "<执行审核人姓名>"
```

`confirm`会把成功文档从“候选”转为“正式”，并把确认绑定到本轮结果。普通的“ok”“继续”不算验收确认。

### 4. 二选一完成

只维护本地结果，不上线：

```bash
python3 <MAINTAIN_SKILL_ROOT>/scripts/run_maintenance.py \
  --job <增量任务目录> --stage commit
```

蒸馏后的最终Wiki上线到钉钉：

```bash
python3 <MAINTAIN_SKILL_ROOT>/scripts/run_maintenance.py \
  --job <增量任务目录> --stage publish --publish-workers 30
```

`publish`会依次发布、回读、检查远程目录树，全部通过后才更新成功基线。发布目标只认全量任务原`task-config.yaml`中已锁定的链接。

## 变化处理

- 新增：完整执行Raw准入、抽取、画像、关系、页面和索引。
- 更新时间变化：重新取得内容；提取文字哈希变化才重做AI画像。
- 每月哈希对账：可加`--hash-audit all`重新取得全部内容；哈希一致时复用AI缓存。
- 源文件变化但提取文字一致：复用AI画像，只刷新来源信息、页面和必要关系证据。
- 改名或移动：刷新来源画像、目录上下文、双目录页面和索引。
- 权限变化：只检测和报告可见范围风险，不修改线上权限。
- 连续两次未发现：列为“来源失联待确认”，不自动删除或判定失效。
- 长期未更新、出现废止/替代词或关系冲突：只形成负责人确认清单。

## 完成时必须告诉用户

读取`00-增量结果与下一步.md`、`01-本次增量审核入口.md`和`06-reports/知识库健康检查.md`，在AI对话框用日常语言直接说明：

- 新增、正文变化、改名/移动、权限变化、失联和未变化数量；
- 本轮实际处理及失败数量；
- 需要立即处理、建议尽快处理、一般提醒和新发现冲突的数量；
- 当前停在“待审核”“已确认”“仅本地提交”还是“已发布并回读通过”；
- 用户下一步只需做什么，并给出本地审核入口或原文链接。

只要尚未明确确认、存在解析失败、发布/回读失败、来源失联待确认或高风险冲突，必须直说“当前仍待处理，不能视为全部完成”。

## 对用户说话的规则

- 先说结果，再说用户下一步；通常控制在6条以内。
- 用户没有主动追问时，不说运行编号、哈希、基线、缓存、Schema、Raw、P0/P1/P2、L0/L1/L2/L3或命令阶段名。
- 把“更新成功基线”说成“把本次结果保存为下次检查的对比依据”。
- 把“P0/P1/P2”分别说成“需要立即处理、建议尽快处理、一般提醒”。
- 把“Raw准入失败”说成“文件不符合收集要求，暂时没有处理”。
- 把“关系孤立”说成“暂未发现明确关联文档”，不要暗示文档有错误。
- 给出可点击的审核入口或原文链接，不向用户展示内部文件编号；只有排查问题时才补充技术信息。
