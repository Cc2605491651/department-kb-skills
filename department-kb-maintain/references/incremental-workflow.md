# 增量维护工作流

## 两套状态

| 状态 | 用途 | 何时更新 |
|---|---|---|
| 观察状态 | 记录本次实际看到的来源节点和连续失联次数 | 每次只读扫描后更新 |
| 成功状态 | 记录已经明确确认，并完成本地提交或线上回读的内容 | 全部必需门禁通过后更新 |

差异必须与成功状态比较，不能只与上一次扫描比较。否则一次处理失败后，下次可能误认为已经处理。

## 稳定身份和指纹

- 文档身份：沿用全量Skill的稳定ID，即`SHA-256(workspace_id + ":" + node_id)`前12位大写十六进制并加部门前缀。
- 文件变化：`source_hash`是原始文件字节哈希。
- 文字变化：`extracted_hash`是规范化提取文字的哈希，是是否重做AI内容画像的主要依据。
- `update_time`只负责召回需要重新取得内容的文档；不能直接证明正文已经变化。
- 每月可用`--hash-audit all`不依赖更新时间重新取得全部内容，覆盖上游更新时间异常的少数情况；哈希未变化时不重复生成AI画像。
- 路径变化：比较`source_path`和`path_hash`。
- 元数据变化：比较标题、类型、创建者和来源时间组成的`metadata_hash`。
- 权限变化：比较规范化权限快照的`permission_hash`；权限无法取得时记录盲区，不用空值覆盖历史指纹。

## 变化分类

| change_type | 判断 | 动作 |
|---|---|---|
| `new` | 当前存在，成功状态不存在 | 完整局部蒸馏 |
| `content_check` | 更新时间变化 | 重新抽取并计算哈希 |
| `content_changed` | 重新抽取后正文哈希变化 | 重算画像、关系和页面，状态回到候选 |
| `file_changed_text_unchanged` | 原文件哈希变化但提取文字哈希相同 | 复用AI画像，刷新来源信息和页面 |
| `metadata_only` | 更新时间变化但正文哈希相同 | 只刷新来源画像和页面 |
| `renamed` | 稳定ID相同、标题变化 | 刷新页面与索引 |
| `moved` | 稳定ID相同、路径变化 | 刷新双目录、索引和R10上下文 |
| `permission_changed` | 权限指纹变化 | 重查关系可见性与泄漏风险 |
| `restored` | 曾失联的稳定ID重新出现 | 恢复处理并复审关系 |
| `suspected_missing` | 本次未看到但未达到连续次数 | 仅告警，不改业务状态 |
| `source_orphan` | 连续失联达到配置次数 | 负责人确认失效、历史保留或权限恢复 |
| `unchanged` | 所有可比较指纹一致 | 全部复用 |

一份文档可同时包含`renamed`、`moved`和`permission_changed`等多个标记；主分类按风险最高动作展示。

## 受影响范围

新增或正文变化文档需要复审：现有一跳关系、直接引用/被引用、相同业务编号、相同版本主体、输入输出匹配、类型互补和检索相似度靠前的候选。改名或移动至少重算标题引用、路径上下文和目录索引。权限变化至少重查已发布关系的两端可见范围。

关系候选可以在本地全量快速重建；Codex核验必须按双方内容哈希、候选证据、提示词和Schema组成输入哈希复用缓存，未变化关系不得重复消耗Token。

## 审核与基线提交

1. 全量引擎本地验收通过后，增量Skill记录当前`run_id`、扫描快照、计划哈希、工作清单哈希和验收哈希。
2. 执行审核人在AI对话框明确确认，记录确认原话、姓名和时间；任一哈希变化都会使确认失效。
3. 仅本地任务执行`commit`后提交成功状态。
4. 上线任务执行`publish`，且本次发布失败数为0、回读失败数为0、远程目录树检查通过后提交成功状态。

未通过时保留旧成功状态与本次观察状态，下次继续处理同一变化。`all`永远不自动确认、不自动发布、不自动提交。
